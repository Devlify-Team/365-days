# A guide to community discussions

## Choose the right place

Start by reading the community's contributing guide, code of conduct, pinned posts, and category descriptions. Search for an existing conversation before opening a new one.

Use a question-and-answer category when you need help and can describe the problem. Use an open discussion for exploration, feedback, or a broad idea. Use an announcement category only when the community permits it. A concrete bug report or scoped task may belong in an issue; code-specific review belongs in a pull request. If the community uses Discord, Slack, or a forum instead, follow its channel purpose and search conventions.

## Ask a question people can answer

Give the post a specific title. State the goal, relevant setup or context, what you tried, and the exact question. Include only the smallest useful error excerpt or code sample, and redact credentials, personal information, and private data. Say what result you expected and what happened instead.

Be concise but do not leave out context a reader needs to reproduce the problem. If your question depends on a version or environment, mention it. Do not assume that maintainers know your local setup.

## Join an existing conversation

Read the original post and earlier replies before responding. Address the point being discussed, explain your reasoning, and link to a source when it helps. If you disagree, respond to the idea rather than judging the person. Ask a focused follow-up when details are unclear, and avoid repeated pings when someone has not replied yet.

When an answer resolves a question, thank the contributor and add a concise note about what worked. In a GitHub question-and-answer category, the author or an eligible maintainer can mark a response as the answer; not every category supports this.

## Turn discussion into action

A conversation can explore options before anyone commits to a solution. When the community agrees on concrete work, summarize the decision and create or link an issue using the project's process. A discussion is not a promise that maintainers will implement every idea.
